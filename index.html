ROI-Isolated Zero-Watermarking Scheme
for Traffic Surveillance Images

Python · YOLOv8 · OpenCV · DWT/DCT · AES-256-GCM · SHA-256 · HMAC · IPFS · MongoDB Atlas

Code / Docs
The Problem

Traffic surveillance images used as court evidence must remain pixel-perfect. Conventional digital watermarks alter the original image — inadmissible in legal settings. The system is built for forensic investigators and law enforcement agencies that need tamper-proof provenance without touching a single pixel.

My Role

Sole engineer and researcher on this project under ISFCR supervision. I designed the full architecture, selected and tuned all algorithms (YOLOv8 segmentation model selection, DWT level choice, block size for DCT), implemented the AES-256-GCM vault and HMAC audit log, and built the IPFS + MongoDB dual-storage verification gateway.

Key Decisions & Trade-offs
  • Why zero-watermarking vs. visible/invisible watermarking? Legally defensible — zero-watermarking stores the fingerprint externally, never writing to the image.
  • Why 3-level DWT + block DCT? 3 levels gave the best balance of robustness against JPEG compression and noise while maintaining discriminability across different image conditions.
  • Why IPFS + MongoDB dual storage? Decentralisation via IPFS protects against single-server failure; MongoDB provides fast lookup for real-time blacklist screening.
Outcome & Impact
  • ✅ 0 pixel alteration to original surveillance images
  • ✅ Correctly detected pixel-swap tamper attacks with exact tamper localization
  • ✅ 256-bit fingerprint secured with AES-256-GCM and HMAC-signed audit chain
  • ✅ Full redundancy: IPFS + MongoDB Atlas + Google Drive triple-layer storage

01 — Best Project AI Security Graph ML

Temporal Multimodal Software Supply-Chain
Threat Detection Engine

Python · PyTorch · NetworkX · 4-Head HGAT GNN · Temporal LSTM

Source Code

Transitive dependency graph — HGAT GNN intercepts malicious packages before install

The Problem & Who It's For

SolarWinds, EventStream, xz-utils — supply chain attacks slip past static scanners by hiding in transitive dependencies. Built for platform security teams and package registry operators who need a pre-install gatekeeper that reasons over the entire dependency graph, not just the top-level package.

My Role

I designed and built everything solo: the NetworkX dependency graph engine, the 4-head HGAT architecture, the temporal LSTM for release-cadence anomaly detection, and the evaluation pipeline — including shuffled-edge and degree-only controls to validate that the GNN learns graph structure, not just features.

Key Decisions & What Went Wrong
  • Why HGAT over GCN/GAT? Multiple node types (package, maintainer, CVE) need separate attention heads — a homogeneous GCN collapses that signal.
  • Initial accuracy was 51% (baseline level) — the graph had severe class imbalance. Added weighted loss and resampling; accuracy jumped to 84.46%.
  • Synthetic LSTM training: Real timestamped release data was sparse; I generated synthetic sequences from heuristics, which limits generalization — honest limitation documented in the README.
Outcome & Impact
  • 🎯 97.08% recall on held-out test set (baseline: ~51%)
  • 📦 Evaluated 24,666 real PyPI/npm packages
  • 🔗 79,741 transitive edges modelled with PageRank + Blast Radius
  • ✅ 10/10 real-world attack scenarios correctly classified
  • 🧪 Shuffled-edge control confirmed GNN learns structure, not artefacts
